# Workflow 21 — Settings filter dialogs

Evidence: `recordings/android/workflow-settings-filter-buttons-open-their-dialogs.png` shows Manual selected, with a title wrapping to two lines and explanatory text to three while mode tabs and close compete in the same header row. The long form scrolls inside a dialog above the app navigation; its footer wraps both explanation and primary action. `SettingsPage.tsx` uses a persistent `w-48` sidebar and `px-8` content padding. `FilterEditor.tsx` exposes two small inline text actions separated by a pipe, although its `createMode` correctly maps each to the shared dialog. `AiFilterSuggestModal.tsx` uses compact desktop text, an 88vh cap, and a small close hit area.

1. **Give phone Settings the full content width.** At phone widths, replace the persistent left navigation with a full-width category selector above the content, retaining the selected category and a 48px Back to Inbox target. Use 16px horizontal content padding; retain the desktop sidebar on wider screens.
   - Acceptance: at 360px and 390px widths, Filters uses the available width without horizontal scrolling; changing categories and returning to Filters preserves the selected category; desktop navigation remains usable.
2. **Make the two creation choices explicit and tappable.** Replace the inline links and pipe with stacked, full-width, minimum-48px buttons labeled “Create filter manually” and “Create filter with AI”. Keep existing `createMode` behavior, with a clear selected state when switching modes in the dialog.
   - Acceptance: each entry opens the matching mode on first tap and after closing/reopening; neither label clips at 360px; screen readers announce distinct action names and the selected mode; manual creation works without AI configuration.
3. **Adapt the wizard to a phone sheet with dependable navigation.** Use the available safe-area height and a single scrollable form; place the title and 48px labeled close target in the first row and full-width Manual/AI tabs below. Use readable 16px form text, minimum-48px inputs and checkbox label rows. Keep a compact footer with a visible primary action and 48px Cancel/Back target; show “Back to edit” from review, preserving entered values. Avoid consuming footer space with redundant instructional text.
   - Acceptance: at 360×640 with keyboard open, focused inputs scroll into view and Preview/Continue remains reachable; title, tabs and close never overlap; every field, action and affected-email review can be reached without horizontal scrolling. Close/Cancel returns to Filters without saving; review Back restores inputs. Android Back dismisses the dialog before leaving Settings, and background content cannot receive taps while the dialog is open.

Validation required after implementation: replay Manual and AI entry → edit/prompt → review → back → close on an Android phone viewport, including the keyboard and safe-area insets. These are design acceptance criteria; this review did not execute a new device test.

## Implementation status

Implemented in `SettingsPage.tsx`, `FilterEditor.tsx`, and `AiFilterSuggestModal.tsx` using `useAndroidMobile`: full-width phone Settings with horizontally scrollable labeled categories; explicit stacked Manual/AI creation choices; full-height filter sheet sized to the Android visible viewport; separate mode row; readable single-column fields with associated labels; 48px controls and checkbox rows; single body scroll and stacked footer actions; native Back/Escape dismissal, focus containment, and focus restoration.

Shared review now defaults retroactive application off, retrieves the complete matching set (the engine reads all account messages and uses its limit only for a JS comparison), renders at most 50 previews with truthful total copy, and applies the complete unique thread set only after opt-in. Pending/failed previews block creation; failed previews do not claim zero matches. A synchronous saving guard blocks duplicate taps. Existing asynchronous sync request behavior remains; the UI makes no confirmed-sync claim.

Validation: targeted filter tests cover desktop and Android entry choices, semantic fields/native Back, 51 matching messages versus 50 rendered previews, explicit retroactive consent, future-only save, and failed preview blocking. TypeScript check passes. Device replay with the software keyboard, 200% text scaling, and TalkBack remains outstanding. Progressive “More conditions” and conditional new-folder disclosure, persistent sync failure/retry status, and post-insert partial-failure recovery remain deferred; the current fields stay directly available and edits survive review Back.
