# Storyboard 18 — One-click Unsubscribe

## Evidence

- `recordings/android/storyboard-18-one-click-unsubscribe.png` shows Inbox, **19 conversations**, and a **Conversation archived · Undo** toast. No unsubscribe control, sender confirmation, or unsubscribe result is visible. The frame proves archive feedback appeared, not that a subscription ended.
- `ActionBar.tsx:210–252` chooses the first message carrying an unsubscribe header. On reported success it silently creates a sender-wide auto-archive filter and archives the thread; failure resets to idle without visible explanation. Its phone action is labeled **Unsubscribe** inside More, which closes immediately on tap. The other toolbar rendering uses an icon-only button.
- `MessageItem.tsx:327–386` provides a labeled but small `text-xs` inline button with minimal vertical padding and independent pending/error state. Its retry copy says **click**. Neither surface exposes the destination before acting.
- `unsubscribeManager.ts:49–145` treats successful POST, sent email, and merely opening a browser as `success`, records each as **unsubscribed**, and returns its method. Both UI surfaces collapse these distinct outcomes into **Unsubscribed**. `emailActions.ts` supplies the archive toast seen in the recording.

## Three phone-touch improvements

1. **Expose one labeled sender action.** Beside the expanded message's sender details, show a persistent **Unsubscribe** button with a minimum 48×48 CSS px touch area. Keep the labeled More entry as a secondary route; both must target the same identified message and share state. Under the sender, show the full sender address and a compact destination line before the tap: **Request to newsletter.example** for POST, **Email to unsubscribe@example.com** for mail, or **Opens newsletter.example** for browser. Use the actual parsed destination; never expose URL tokens. In mixed-sender threads, bind each action to its displayed sender instead of silently choosing the first eligible message.
   - **Acceptance:** At 360px width, the label and destination remain readable without horizontal scrolling; long addresses wrap. A finger can activate the control without opening More. Tapping either route acts on the displayed sender/header, including in mixed-sender threads. Messages without an actionable header show no active unsubscribe button.

2. **Keep pending and retry feedback in the reader.** On tap, change the sender action to **Sending request…**, disable both routes for that operation, and keep a visible inline status even when More closes. On failure, show **Couldn't send unsubscribe request · Retry** with a 48px Retry target; browser-opening failures instead say **Couldn't open unsubscribe page · Retry**. Replace “click” with touch-neutral copy. Announce status politely without moving focus; reset/bind status when account, sender, or thread changes.
   - **Acceptance:** A slow request visibly remains pending and repeated taps issue one operation. Offline or rejected requests show a persistent, retryable error rather than silently returning to idle. Retry uses the same sender/destination. Switching threads never carries another sender's pending or completed label into the new reader.

3. **Report the actual outcome and preserve the message.** Remove automatic archive and automatic filter creation from unsubscribe. After accepted POST, show **Unsubscribe request accepted by newsletter.example**; after mail, **Unsubscribe email sent to unsubscribe@example.com**; after browser handoff, **Unsubscribe page opened · Complete the steps there**. Keep corresponding stored outcomes distinct so reopening cannot falsely show a confirmed subscription end. Leave Archive available as its separate existing action; do not offer an unsubscribe Undo that only reverses archive.
   - **Acceptance:** Exercise POST acceptance, mail send, browser handoff, and total failure: each produces its matching visible and stored outcome; browser handoff never says **Unsubscribed**. Inbox membership/count and sender filters stay unchanged after every unsubscribe route. The reader remains open, no **Conversation archived** toast appears, and future mail remains visible unless the user separately chose an archive rule.
