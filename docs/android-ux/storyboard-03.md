# Storyboard 03 — Reply to Sender

## Evidence reviewed

- `recordings/android/storyboard-3-reply-to-sender.png` (1080 × 2400): after returning to the thread, the software keyboard remains open; the lower reply controls sit behind the app's bottom navigation. The full timestamp competes with sender identity: the sender name is rendered as “Sara...” and the adjacent address is truncated. The Reply All action is visually prominent, despite this being a sender-only reply journey.
- Representative MP4 frames sampled at 0, 3 and 6 seconds from `recordings/android/storyboard-3-reply-to-sender.mp4` (9.67 seconds): initial loading, thread transition, then composer with entered reply and keyboard. At approximately 6 seconds, Send is visible directly above the keyboard, a useful behavior to preserve. The static final image establishes the keyboard-dismissal defect; these samples do not prove delivery or the exact moment of sending.
- `src/components/email/ActionBar.tsx`: reply actions already provide 48px mobile targets, but compete in a horizontally scrolling toolbar with destructive and organizational actions.
- `src/components/email/InlineReply.tsx`: activation focuses after a 50ms timer and separately scrolls once on mode change; keyboard resize can happen afterward. Editor is 14px and capped at 200px. Header controls are 36px; footer Send/Expand do not establish a minimum touch height. Send is labeled with the mode (“Reply”), then clears content and collapses without explicitly blurring. No quoted-context disclosure exists in this component.
- `src/components/email/MessageItem.tsx`: full date is non-wrapping and non-shrinking beside sender; the address appears both beside and below the name on small screens.
- `src/components/composer/Composer.tsx`: mobile composer uses 100dvh and a scrollable editor with a fixed flex footer; Send already has a 48px mobile target. Quote disclosure already exists with expanded state and sanitized content. The send callback queues the message for an undo delay; closing the composer alone does not explicitly release editor focus.

## Proposed interaction

Tap a clearly labeled Reply action. Show “Reply to Sarah” and a recipient address that can be expanded without altering the draft. Focus the response editor, keep its caret and Send above the keyboard, and collapse previous-message context behind “Show original message.” After Send queues successfully, blur the editor, dismiss the keyboard, return to the same thread, and announce “Sending — Undo available.” Announce “Sent” only after the actual send succeeds. If sending fails, retain a recoverable draft and show a visible retry action.

## Exact implementation changes

1. **Reliable keyboard and Send behavior** — in `InlineReply.tsx` and `Composer.tsx`, explicitly blur the Tiptap editor and active editable element after successful queue creation, before clearing/collapsing or closing. Use the project's existing native keyboard abstraction if present; do not add a dependency solely for dismissal. Do not blur on validation failure. Keep editor content available for undo/retry until delivery resolution. In inline mode, change the primary button label to **Send**, give it a 48px minimum height and a sending state, and preserve the existing duplicate-send guard. Surface delayed-send failures through visible status rather than console logging alone. Expose queue/success/failure status through a polite live region. Keyboard dismissal must also occur on explicit close/cancel, without accidentally sending.
2. **One usable editing viewport** — in `InlineReply.tsx`, replace the crowded mobile single-row mode/recipient/expand/cancel header with a wrapping two-row arrangement: mode and close/expand first, recipient summary second. Set mobile interactive targets to at least 48 × 48 CSS px (text controls may be wider); use 16px body text. Keep Send in a non-shrinking footer inside the keyboard-adjusted editing viewport. Re-scroll the caret after keyboard viewport resize using the application's shared viewport handling; clean up listeners and avoid focus-stealing repeated timers. In `Composer.tsx`, preserve the existing 48px Send target and scrollable body, but let optional footer controls wrap or move to an overflow menu at narrow widths so Send never leaves the viewport. The thread's global bottom navigation must not overlap an active editor.
3. **Clear recipient and context** — in `ActionBar.tsx`, keep sender-only Reply explicit and distinct from Reply All; retain large targets and accessible names. In `MessageItem.tsx`, use a short mobile date and move full date into expanded metadata; render the address once on mobile and allow full sender identity to wrap. In `InlineReply.tsx`, add a collapsed, sanitized, read-only “Show original message” disclosure with `aria-expanded` and `aria-controls`, including sender and date. Keep quote display separate from editable reply text and preserve existing outgoing-message behavior unless an explicit quote feature is implemented. In `Composer.tsx`, retain current quoted HTML inclusion and disclosure semantics; opening and closing context must not mutate the reply or quote. Transfer draft body, recipients, threading identifiers and quote/context state when expanding inline reply.
   **Accessibility within these changes** — label each rich-text editor “Reply message,” with textbox/multiline semantics; give mode controls selected state, full-address recipient disclosure an accessible name, and all icon-only actions explicit labels. Preserve visible focus rings. Return focus to the invoking Reply control after cancel and to a stable thread heading or status after send without focusing another text field. Respect reduced motion when scrolling into view. Keep the Send/Undo sequence usable by TalkBack and an external keyboard.

## Acceptance criteria

- At 320px, 360px and 412px CSS viewport widths, Reply can be activated without horizontal scrolling; sender identity, recipient disclosure and Send do not overlap or clip.
- With the Android keyboard open, the active caret and 48px Send control remain visible in portrait and landscape; typing a long reply scrolls the editor rather than hiding Send. Opening context does not steal editor focus or hide Send.
- Sender-only Reply addresses the message's Reply-To when provided, otherwise From; no other thread recipients are added. Switching modes is explicitly announced and does not clear typed text.
- One tap sends once. The keyboard closes after queueing and remains closed on return to the thread, reproducing the final screenshot with the keyboard absent. Queue validation errors preserve focus and text; transport errors offer retry and retain the response.
- Original-message disclosure opens and closes without changing authored text. Expanding to the full composer preserves content, recipient selection and thread association; quoted content is sanitized and is never duplicated in outgoing mail.
- TalkBack identifies Reply, recipient address, Reply message, original-message disclosure and Send in a logical order; it announces queued, sent and failure outcomes accurately. Cancel returns to the invoking action. All mobile editor actions meet 48px target sizing and support visible keyboard focus.
- Verify on the actual Android WebView with a software keyboard, including Back to dismiss keyboard, then Back to close editor. Existing send/undo behavior must remain intact. A passing scripted send assertion alone does not verify keyboard visibility or reachable controls.
