# Storyboard 19 — Spam / Phishing Safety

## Evidence

- `recordings/android/storyboard-19-report-spam-phishing-safety.png` shows **Spam**, **1 conversation**, and “URGENT: Verify Your Bank Account Immediately” with the preview “Suspicious request to verify credentials.” This verifies the visible destination, but does not show a warning, reporting gesture, or confirmation.
- `AuthWarningBanner.tsx` shows an alert only for aggregate authentication failure. Its 12px explanation embeds SPF/DKIM/DMARC; the address uses 11px text. **Report Spam** and **Move to Spam** call the same callback, while **I trust this sender** shares their wrapping action row and falls back to dismissing the warning. Dismiss is a small padded icon and technical details have a 36px minimum target.
- `ActionBar.tsx` puts labeled **Report spam** late in the Android More menu; the primary five-button row has no spam action. `handleSpam` delegates to `spamThread`, so completion/error feedback must be verified through that shared action rather than inferred from this screenshot.

## Three phone-touch improvements

1. **Make the warning readable and immediately actionable.** Above message content, use **Sender couldn't be verified** and **This message may be pretending to be someone else. Avoid links and attachments unless you verify the sender another way.** Show the full wrapping sender address, 16px body text, and a distinct **Why was this flagged?** disclosure for authentication details. Give disclosure and dismiss controls 48×48px touch areas; dismiss only hides this warning.
   - **Acceptance:** At 360px width and enlarged system text, warning, address, and controls wrap without clipping or horizontal scrolling. Warning meaning survives without color. TalkBack announces the warning once; disclosure exposes expanded state and readable verification results. Dismiss never trusts the sender or changes folder membership.

2. **Provide one safe primary action and separate Trust.** Replace the duplicate banner spam buttons with one full-width **Report spam** button, minimum 48px high. Keep the same labeled action in More; position it before lower-priority scheduling actions. Put **Trust sender…** on a separate secondary row, at least 12px from Report spam, and only expose it when a real trust handler exists. Open a confirmation identifying the sender and explaining the actual scope of trust, with **Cancel** and **Trust sender**; never silently substitute dismiss.
   - **Acceptance:** A flagged message exposes Report spam without opening More. Both entry points invoke one shared operation, and repeated taps while pending cannot report twice. Every interactive target is at least 48×48px. Trust requires its separate confirmation; Cancel preserves warning and trust state. Reporting never trusts the sender, and dismissing never executes either action.

3. **Confirm the result and make Spam reachable.** On report, display **Reporting spam…** and then **Moved to Spam**, with a labeled **View Spam** action opening the current account's Spam folder. Preserve the list destination/count shown in the storyboard and keep Spam reachable from Folders. Failed reports retain the message and show **Couldn't report spam · Retry**. In Spam, relabel the action **Not spam** and confirm its resulting Inbox destination separately; trust and Not spam remain distinct.
   - **Acceptance:** Successful report removes the thread from Inbox and View Spam reveals that same thread under Spam with an updated count. Offline/rejected operations show no success claim or permanent removal and offer a 48px Retry target. Status is announced accessibly and remains available long enough to act. Report, retry, and Not spam use the current account; changing accounts or threads never displays another operation's status. Capture warning → report → feedback → Spam, since the supplied frame establishes only the final folder view.
