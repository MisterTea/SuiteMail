# Storyboard 16 — Attach Files & Attachment Library

## Evidence

- `recordings/android/storyboard-16-attach-files-attachment-library.png` shows one PDF, its filename, sender and 1.0 MB size. Search plus four filters occupy several header rows; a large decorative file canvas dominates the result. Preview, download and source-email icons are visible but small. The frame establishes library display only, not successful file selection, upload, download or opening. Its “57y ago” date also needs validation against fixture timestamps before being treated as a real message age.
- `src/components/attachments/AttachmentLibrary.tsx` defaults to grid; four small select controls and a compact view toggle wrap in the header. Load/download failures only reach the console, so a failed load can resemble an empty library.
- `AttachmentGridItem.tsx` and `AttachmentListItem.tsx` already expose actions on phones (`opacity-100`), but their icon buttons use small padding. The list puts filename, extension, fixed-width size and three actions on one horizontal line, leaving little filename space. Sender/date disappear below `md`.
- `src/components/email/AttachmentList.tsx` already makes message attachment chips full-width on phones, with type/size metadata and visible actions; action targets are only 36px. Preview errors have text but no Retry; save failures are console-only. These shared surfaces should use the same phone file-row behavior.

## Three phone-touch improvements

1. **Default to readable file rows.** Below 640px, open the library in list mode with no decorative preview canvas. Use a full-width, vertically stacked row: 16px filename (up to two lines), then explicit type and formatted size, then sender/date. Preserve the extension when shortening long names and expose the complete filename in file details; unknown metadata reads “Unknown type” / “Size unavailable.” Keep optional grid view in the filter sheet rather than spending header space on tiny icons. Apply the same filename/type/size hierarchy to received and selected-file rows.
   - **Acceptance:** At 360px and 200% text size, a long filename, PDF/XLSX/ZIP type and size remain distinguishable without horizontal scrolling or overlapping actions. Multiple files form one vertical list; opening file details reveals the full filename. Unknown sizes never display as zero bytes. No claim of successful attachment/upload is made from this library-only frame.

2. **Make file actions explicit and recoverable.** Place labeled **Open** (previewable files) and **Download** buttons below each row’s metadata, each at least 48px high with 8px separation; put **View email** in a labeled overflow action. Unsupported files offer Download plus “Preview unavailable”; row taps open details rather than unexpectedly starting a download. Use the same actions in message attachments and preview. Show per-file “Downloading…” and disable duplicate starts; report success only after the save outcome is known. On fetch/save failure, keep the row and show “Couldn't download [filename] · Retry.” Canceled system saves return quietly. Preview gets Retry and a persistent Download alternative.
   - **Acceptance:** Every available primary action is visible without hover or long press and has a minimum 48×48px touch target and file-specific accessible name. Tapping Download never also opens the row. Offline and save-error tests show actionable feedback while preserving the list and scroll position. Retrying succeeds without duplicate concurrent requests. Android Back closes preview to the same row; unavailable remote identifiers produce a visible unavailable state rather than a silent no-op.

3. **Put search and filters within reach; distinguish failure from empty.** Keep a 48px-high full-width search field and a single 48px **Filters (n)** button above results. Open a bottom sheet containing labeled Type, Sender, Date and Size controls, with 48px rows, **Clear all** and **Show results**; show applied filters as removable summary chips. Preserve search/filter choices on preview return. A load failure displays “Couldn't load attachments” and Retry, separately from “No attachments yet”; zero matches offers Clear filters. Clear stale results on account switch or keep them hidden until the new account finishes loading.
   - **Acceptance:** On a 360px phone, all four filters can be reached and changed without horizontal scrolling; the sheet scrolls above navigation/system insets, and its actions stay reachable with keyboard open. Back dismisses keyboard then sheet without losing choices. Applied count and results match after Show results. Clear filters restores unfiltered results. A failed initial load never displays No attachments yet, and switching accounts never exposes the previous account's files.

## Implementation status (2026-11-20)

Implemented in Android phone mode via `useAndroidMobile`: library starts in list view; file rows show wrapping full filenames, explicit file type/size, sender/date and visible labeled 48px Open, Download and View email actions. Received attachments use wrapping filenames and labeled Open/Download controls. Library and message downloads expose errors; library load failure has Reload and no false empty state. Existing filters have 48px phone targets. Desktop layout remains on its prior path.

Deferred: consolidated filter bottom sheet/chips, per-file library progress/retry and success/cancel distinction, full file-details behavior, preview retry, cross-account stale-load protection, and upload/selected-file composer changes. No native picker or background transfer implementation is claimed. Device verification at enlarged text/keyboard sizes remains necessary.

Validation: targeted supporting-flow component tests plus Android-specific Trust confirmation and past schedule validation regression tests; TypeScript check run alongside integration. See implementation report for final results.
